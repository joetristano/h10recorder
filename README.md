# Heart Monitor Recorder

Single-file web app that records live heart rate, RR intervals and HRV from any standard BLE heart-rate strap (Polar H10, WHOOP with Heart Rate Broadcast, etc.), plus raw ECG and accelerometer on the Polar H10. Shows heart-rate zones and exports a CSV.

## Use
- Needs a Web Bluetooth browser: Chrome/Edge on desktop or Android, or **Bluefy** on iOS (Safari doesn’t support it).
- Must be served over HTTPS (GitHub Pages works).
- Wet the strap electrodes, close Polar Beat/Flow, tap **Connect**, then **Start/Stop recording** and **Share CSV**.

## v7 — Whoop history sync: skin temp (2026-11-25, pushed to muse branch commit PENDING, verified live PENDING)
- **Skin temp is in the history, not the live stream — verified, not assumed.** The live 0x28 record has no temp field (Rudra's `Realtime` struct reads only offsets 0–11; the ZHOOP blog: "HRV, recovery, sleep, temperature, and the PPG waveform are *not* streamed live; they come out of the historical store"). The temp lives in the v18 biometric history record: skin temp u16 at frame offset 73 (packet offset 65) / 128 = °C, from the AS6221 sensor. Verified against the blog's real captured frame (HR 102, RR [602, 613] ms, temp raw 3057 → 23.9 °C, |g| 1.009). Trend is reliable; absolute °C calibration is unverified — the card labels it "(history)".
- **Sync history button (5.0/MG only):** on the Whoop card, enabled once the direct link is up. Tap it and the app pauses the live stream (one BLE link can't do live + history), sets the band clock (best effort), enters high-frequency sync (0x60), sends SEND_HISTORICAL_DATA (0x16, [0x00]), then streams the ~14-day store chunk by chunk. Every HISTORY_END is ACKed with HISTORICAL_DATA_RESULT (0x17, [0x01]+cursor) — skip the ACK and the strap re-serves the chunk forever. Metadata meta_type: 1 START, 2 END, 3 COMPLETE; cursor at frame[21:29]. On COMPLETE it exits high-freq sync (0x61) and turns the live stream back on. A 20 s stall aborts (ABORT_HISTORICAL_TRANSMITS 0x14) and restores the live stream; tapping the button again stops it. During a sync the long 0x28 variant is ignored (its HR sits at offset 22, so the compact parser would misread it).
- **What it shows:** the Whoop card's skin-temp tile fills with the latest v18 temp and the sync line counts records ("receiving… 1,234 records · skin temp 23.9 °C"). v26 PPG records are counted, not decoded. 4.0 history (different V24 layout) is not built — the button says so.
- **Tests:** `~/workspace/h10recorder-tests/test_whoop.js`, **45/45** — v18 parse from the blog's verified vector, metadata START/END cursor, ACK frame inner bytes, temp tile fills only while syncing, 0x28 skipped during sync, END → ACK written, COMPLETE → sync stops and live stream resumes; all v6.5 tests still pass.

## v6.3 — Whoop 5.0 realtime 0x28 + response fix + bonding note (2026-11-25, pushed to muse branch commit fd8af88b, verified live 2026-11-25 08:25 EST: branch source checked directly — 0x28 flag parse, status 0x01, frames counter present, old tick conversion gone; Strain card present on the live page)
- **Live result:** v6.1's test reported `hello: Whoop command 0x91 timed out cmd:[writeWithoutResponse,write] resp:[notify] data:[notify]`, 0 packets, 0 frames rejected — the hello write went out but the band never answered. Two hardware-verified sources the user sent (Rudra5417/whoop5-protocol + the ZHOOP blog, rusheelraj.com/blog/whoop) explain it: the strap holds **one encrypted bond**, created by pairing in the official WHOOP app — a third-party app on iOS has no way to create it, and without it the band silently discards the hello. Command responses are type 0x24 `[type][seq][cmd][counter][status][payload…]` — byte 3 is a counter, not the request seq, so responses now match on command alone and success is status `0x01`. The static hello frame itself is confirmed byte-for-byte by both sources (unchanged).
- **Also folded in from v6.2 (never pushed separately):** `whoopWrite` retries the confirmed write 3 times before falling back and reports which method sent the frame ("timed out via write" vs "via writeWithoutResponse"); the hello gets 15 s for bonding; the card gains a "N frames" counter for verified frames of any type; the card title is set as soon as the family is known, so a failed 5.0 attempt reads "Whoop 5.0/MG". The Whoop card's info panel now states the bond requirement.
- **Tests:** `~/workspace/h10recorder-tests/test_whoop.js` (durable copy — `/tmp` is wiped on restarts, so the earlier per-version suites are gone), **24/24** — 0x28 flag 0/1/2, wrong version ignored, HR range, 4.0 realtime regression, cmd-only response matching, status failure, write retry/fallback, method in the timeout message, family detection from the user's exact service list, title set on detection, hello frame exact.

## v5 — Whoop 4.0 re-port from the real protocol (2026-11-25, pushed to muse branch commit 578f9b7b, verified live 2026-11-25 via browser check 07:47 EST + the user's own paste)
- **The whoop-reader port was wrong, three ways.** v4.3's "not among 4 services" diagnostic cracked it: the band never exposed the `...8000` service because the real 4.0 service is `61080001-8d6d-82b8-614a-1c8cb0f8dcc6` — every UUID in the old port was off by one (service `...8001`, command `...8002`, response `...8003`, event `...8004`, data `...8005`). The frame envelope was wrong too: the real 4.0 envelope is `[0xAA][length u16 LE][CRC8 over the length bytes][type][seq][cmd][payload][standard zlib CRC32]`, not whoop-reader's `[0xAA][cmd][length][payload][custom-XOR CRC32]` — and there is no 96-byte packet; notifications arrive MTU-fragmented and must be reassembled. Third, the custom channels only flow once the link is bonded, which happens on the first confirmed write. Source: NOOP's hardware-verified protocol doc (johnmiddleton12/my-whoop), cross-checked against a sniffer capture of a real 4.0's HELLO frame.
- **What v5 does:** `findWhoopService` now looks for `...8001`; commands are built with the real envelope (CRC8 poly 0x07 + standard CRC32); a reassembler collects fragmented notifications into verified frames; the connect flow is bond (confirmed `GET_BATTERY_LEVEL`, cmd 26 — also reads battery, u16 at payload bytes 2–3 / 10) → `GET_HELLO_HARVARD` (cmd 35) → `TOGGLE_REALTIME_HR` (cmd 3, `[0x01]`). The failure diagnostic now lists the discovered service UUIDs (short form), so a 5.0/MG band (`fd4b0001`, a different protocol) would show up by name instead of hiding behind a count.
- **Honest scope change:** the live stream (type-40) carries heart rate and RR intervals only — no SpO2, no skin temp, no accelerometer. Those live in the band's stored history (type-47 offload, not built). The Whoop card's SpO2/temp tiles are gone; the Accelerometer card is Polar-only again. SpO2/temp/accel from v4–v4.1 were decoded from a packet layout that doesn't exist on the wire.
- **Tests:** `/tmp/test_whoop5.js`, 22/22 — CRC8/CRC32 and the full frame verified against the sniffer-captured HELLO frame, frame build/verify round trip, reassembler (whole, split + garbage, corrupt), command round trip with battery decoding 82.0%, short-UUID formatting.

## v4.3 — Whoop link iOS fix (2026-11-25, pushed to muse branch commit a34bad4d, verified live via the user's paste + browser check)
- **Why:** the first live test on a real 4.0 (WHOOP 5AM0079283, Bluefy on iOS) reported "direct link failed (find service: 2)" — `getPrimaryService` for the custom service failed with a bare numeric error while standard HR and battery worked. Reviewed [christianmeurer/whoop-reader](https://github.com/christianmeurer/whoop-reader) again: the UUIDs match character-for-character, so the port is right. The difference is how the service is established — bleak connects by address, does full GATT discovery inside `connect()`, and addresses characteristics directly by UUID; it never does a separate get-primary-service step. The web app's separate `getPrimaryService` step is the thing that fails on iOS Web Bluetooth wrappers (Bluefy), where service discovery right after connect is flaky.
- **The fix:** a new `findWhoopService()` helper — wait 500 ms after connecting, retry the direct `getPrimaryService` lookup up to 3 times, then fall back to enumerating all primary services with `getPrimaryServices()` and matching by UUID (the bleak approach). If even the enumeration doesn't list the service, the diagnostic now says so ("not among N services") instead of a bare number.

## v4 — Whoop 4.0 direct BLE (2026-11-21, pushed to muse branch commit fe2bdff2, verified live)
- **Direct link, no broadcast needed:** when the connected device exposes Whoop's custom BLE service (`61080000-8d6d-82b8-614a-1c8cb0f8dcc6`), the app talks to it directly using the community reverse-engineered protocol from [christianmeurer/whoop-reader](https://github.com/christianmeurer/whoop-reader) (MIT) — HELLO handshake, START_REALTIME, then 96-byte real-time packets on characteristic `...8004`. HR (bytes 1–2, ×100) and RR (bytes 3–4, ms) feed the same pipeline as the standard HR service: live HR, zones, HRV, strain, recording.
- **SpO2 and skin temp:** byte 5 (SpO2 %) and byte 6 (skin temp = raw − 25 °C) show in a new Whoop 4.0 card and are recorded to CSV as `spo2` and `temp` rows. Battery is queried with the Whoop command (0x01) instead of the standard battery service.
- **Whoop 3.0 stays the same:** devices without the custom service use the standard heart-rate broadcast path exactly as before — the 4.0 attempt is tried first and silently falls back. The standard HR service is skipped once the 4.0 stream is running, so beats are never double-counted.
- **Unconfirmed accel:** packet bytes 7–12 are candidate accelerometer axes in whoop-reader. They are plotted live in the Accelerometer card (header reads "Whoop 4.0 · raw, unconfirmed" while connected) and recorded raw in the CSV as `wacc` rows — labelled unconfirmed in the app, since the shape is indicative but the scale is raw, not mG.
- **Testing:** the Whoop CRC-32 variant (poly 0x04C11DB7, init FFFFFFFF, xor-out F43F44AC) and all four command frames were cross-checked byte-for-byte against the Python whoop-reader code; a synthetic 96-byte packet (HR 72.34, RR 831, SpO2 97, 36 °C) parses and feeds the live pipeline; corrupt-CRC packets are counted and ignored. 42/42 whoop checks pass; strain (17/17) and info-button (12/12) suites still pass. **Not yet tested against a real Whoop 4.0** — that needs the band on a wrist.

## v3 upgrades — strain (2026-11-21)
- **Live Strain card** (new card after HR zones): Edwards load, Banister TRIMP, and a 0–21 strain score, updating live on every beat while connected and freezing on the recording after Stop.
- **Edwards load** = Σ minutes in zone × weight (Z1=1 … Z5=5, below Z1=0), from the time-in-zone the app already tracks.
- **0–21 score** = 21×(1−e^(−Edwards/150)), a saturating map onto a familiar 0–21 scale. This is our mapping, not WHOOP's (their formula is proprietary) — labelled as such in the app.
- **Banister TRIMP** = duration(min) × ΔHR × 0.64×e^(1.92×ΔHR), ΔHR=(avg HR−resting HR)/(max HR−resting HR). Resting HR is the value entered in the Workout card, else the lowest HR seen; shown as "–" until a resting HR exists.
- **Analysis, sessions, exports:** the ECG analysis summary shows Strain / 21, Edwards load, and Banister TRIMP (zone seconds rebuilt from the HR samples in the CSV, so uploaded files get the same strain); saved sessions list the strain in the drawer; CSV gains `strain` rows (edwards_load, strain_0_21, banister_trimp) and JSON export carries `strain_0_21`, `edwards_load`, `banister_trimp` in metrics.
- **Caveat:** HR-based strain under-reads strength work — a bench session at 97–108 bpm scores low even though the muscular effort is high. Tested: 30 min Z2 + 20 min Z3 + 10 min Z4 → Edwards 160, strain 13.8/21, TRIMP 59.7 (avg 130, rest 58, max 190, 60 min); all 17 strain checks pass, including a units check that caught TRIMP being fed seconds instead of minutes in analysis.

## CSV format
`stream,t_s,v1,v2,v3`
- `ecg`: v1 = µV (130 Hz)
- `acc`: v1,v2,v3 = x,y,z mG (200 Hz)
- `hr`: v1 = bpm, v2 = RR interval ms
- `spo2` (Whoop 4.0 only): v1 = SpO2 %
- `temp` (Whoop 4.0 only): v1 = skin temp °C
- `wacc` (Whoop 4.0 only): v1,v2,v3 = raw accel x,y,z — unconfirmed decoding, recorded only
- `hrv`: summary rows at the end (v1 = value, v2 = metric name)
- `zone`: seconds per heart-rate zone (v1 = seconds, v2 = zone), plus max HR used
- `strain`: Edwards load, 0–21 score, Banister TRIMP (v1 = value, v2 = metric name)

## Protocol notes
Raw ECG/ACC come from Polar’s PMD service (`FB005C80-02E7-F387-1CAD-8ACD2D8DF0C8`): write a start command to the control characteristic (`...5C81`), read notifications on the data characteristic (`...5C82`). HR/RR use the standard Heart Rate service. Whoop uses its own custom service, in two families: 4.0 on `61080001-8d6d-82b8-614a-1c8cb0f8dcc6` (NOOP envelope `[0xAA][length u16 LE][CRC8][type][seq][cmd][payload][standard CRC32]`; bond via a confirmed battery write, then hello cmd 35, then live HR cmd 3) and 5.0/MG on `fd4b0001-cce1-4033-93ce-002d5875f58a` (Format 1 envelope `[0xAA][0x01][declLength u16 LE][00 01][CRC16-Modbus][type][seq][cmd][padded body][standard CRC32]`; static client hello cmd 145, then live HR cmd 3). Live type-40 frames carry HR + RR only (5.0 R-R in 1/1024 s ticks); SpO2/temp live in stored history. Source: NOOP's hardware-verified protocol docs (johnmiddleton12/my-whoop, ryanbr/noop).
